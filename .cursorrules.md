# Cursor Rules - ZYMO Intranet

## Objetivo
Mantener consistencia tecnica y funcional en `zymo-intranet`, respetando lo ya implementado y asegurando que cada cambio quede listo para despliegue en servidor Ubuntu con Docker Compose.

## Principios no negociables
1. Codigo limpio siempre: legible, modular y reusable. Evitar archivos y funciones gigantes.
2. Seguridad por defecto: todo cambio debe reducir riesgo, nunca aumentarlo.
3. Produccion primero: todo cambio debe quedar Docker-ready y compatible con despliegue real.
4. No romper flujos existentes: cambios incrementales, retrocompatibles y con riesgo controlado.
5. Sin deuda oculta: no dejar TODO criticos sin registrar en `docs`.

## Estilo de codigo limpio
- Preferir funciones cortas con una sola responsabilidad.
- Nombrar variables y funciones con semantica de negocio clara.
- Evitar logica duplicada; extraer helpers/utilidades reutilizables.
- Evitar condicionales anidados complejos; usar early return cuando aplique.
- Mantener contratos de API estables; si se cambia contrato, documentar migracion.
- Si una seccion no es obvia, agregar comentario breve y util (no redundante).

## Reglas de arquitectura y alcance
- Respetar separacion de capas:
  - `routers`: transporte HTTP y validacion de entrada/salida.
  - `services`: logica de negocio.
  - `models/database`: persistencia.
  - `frontend hooks/pages/components`: consumo, estado y presentacion.
- No mezclar reglas de negocio complejas dentro de componentes UI.
- Evitar acoplamiento entre modulos sensibles (OC, Financiero, Gerencial, Agentes) sin necesidad real.

## Ciberseguridad obligatoria
- Nunca hardcodear secretos, tokens, passwords, NITs o datos sensibles en codigo fuente.
- Usar variables de entorno para credenciales y configuracion sensible.
- Mantener CORS estricto en produccion (sin comodines inseguros).
- Mantener validacion de entrada en backend (tipos, formatos, permisos).
- No exponer informacion sensible en logs, errores HTTP ni respuestas de debug.
- Mantener respuestas de autenticacion genericas para evitar enumeracion de cuentas.
- Proteger endpoints sensibles con dependencias de permisos/roles.
- Seguir Defense in Depth:
  - red (firewall/fail2ban/nginx),
  - app (rate limit, validacion, lockout),
  - contenedor (sin privilegios innecesarios).

## Reglas Docker y despliegue
- Todo cambio debe funcionar en contenedores, no depender de binarios locales del desarrollador.
- Mantener `docker compose` como fuente de verdad de ejecucion.
- No exponer puertos internos innecesarios al host.
- Evitar cambios que requieran pasos manuales fragiles para iniciar servicios.
- Si se agregan dependencias, verificar build de imagen y arranque del servicio afectado.
- Mantener compatibilidad con volumenes y rutas persistentes ya usadas en servidor.

## Bases de datos y datos
- Cualquier cambio de modelo/tablas debe ser backward compatible o incluir plan de migracion.
- Operaciones destructivas deben ser transaccionales y seguras.
- Para limpieza/purga, proteger tablas core (usuarios, roles, permisos, etc.).
- Optimizar primero consultas SQL e indices antes de introducir complejidad extra.
- Evitar N+1 queries en endpoints de alto uso.

## Reglas para frontend
- UX consistente: sin `alert()` bloqueantes para errores de flujo.
- Usar estados de error/success visibles en UI.
- Evitar elementos hardcodeados cuando existe fuente dinamica desde backend.
- Mantener accesibilidad basica (labels, estados, feedback visible).
- Mantener componentes enfocadas y reutilizables.
- Los estilos nuevos deben ser ajustables y centralizados: preferir tokens, variables CSS, clases/utilidades compartidas y componentes reutilizables antes que valores visuales rigidos dispersos. Cualquier propuesta visual tipo shadcn/Vercel/Claude debe poder cambiarse sin reescribir pantallas completas.

## Observabilidad y auditoria
- Loggear eventos de seguridad y accesos denegados en modulos sensibles.
- Mantener mensajes de log claros y accionables.
- No incluir secretos ni payloads sensibles en logs.
- Si un error es esperado, registrar warning; si compromete operacion, registrar error.

## Flujo de trabajo para cambios
Antes de codificar:
- Revisar impacto en backend, frontend, seguridad y despliegue.
- Confirmar si afecta contratos API, modelos o variables de entorno.

Durante implementacion:
- Hacer cambios pequenos y verificables.
- Priorizar claridad sobre "magia" o sobreingenieria.

Antes de cerrar:
- Verificar build/test minimo del modulo afectado.
- Verificar que sigue desplegable en Docker.
- Verificar que no se introdujeron secretos ni configuraciones inseguras.
- Actualizar `docs` cuando cambie comportamiento, seguridad u operacion.

## Definicion de Done (obligatoria)
Un cambio se considera listo solo si:
- Compila/build pasa en modulo afectado.
- No rompe endpoints/rutas existentes sin justificacion documentada.
- Cumple criterios de seguridad.
- Es desplegable en servidor Docker sin pasos ocultos.
- Queda documentado cuando aplique.

## Antipatrones prohibidos
- Hardcodear secretos o datos corporativos sensibles.
- Funciones/archivos gigantes sin separacion por responsabilidades.
- Soluciones "temporales" sin trazabilidad ni plan de retiro.
- Cambios que solo funcionan en entorno local.
- Bypass de validaciones, permisos o controles de seguridad.

## Regla de continuidad
Si existe conflicto entre velocidad y calidad:
- Gana seguridad y estabilidad.
- Luego se optimiza velocidad de entrega.
